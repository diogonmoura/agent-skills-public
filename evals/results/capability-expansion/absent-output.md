## Proposed behavior and boundaries

1. **Request.** Authenticate the actor, resolve the organization through trusted membership data, and require current owner authority server-side. A role or organization ID supplied by the client never establishes permission. Create an export record with immutable organization and requester IDs, validated selection, state and timestamps. Use the existing API's denial and resource-enumeration conventions. Members, former owners, unauthenticated actors and owners of other organizations must not create, inspect or download this organization's exports. Apply the same policy to list, status, retry and download entry points, including alternate clients.
2. **Durable admission.** Persist the request before dispatch. Follow the existing reliable enqueue mechanism; if transaction commit and enqueue cannot be atomic, use an existing outbox/reconciliation pattern or a small pending-request dispatcher. An enqueue failure must leave recoverable state. Bound simultaneous exports per organization using existing limits; do not invent a numeric quota without demand evidence.
3. **Worker.** Queue only a durable export identifier. Reload its immutable scope and authoritative membership; never trust serialized roles. Claim work atomically so duplicate deliveries cannot publish multiple artifacts. Scope every record, association and attachment query to the export's organization. Stream/batch data with bounded memory and redact secrets or non-exportable internal fields. Do not use an unscoped record lookup followed by filtering in Ruby. Avoid holding membership locks throughout a large export.
4. **Membership changes during work.** A request-time owner check alone is insufficient. Proposed conservative policy: the requester must still own the same organization at worker start and immediately before publication; recheck during long batches to stop wasted work promptly. After demotion/removal, mark the request revoked/cancelled, discard temporary output and prevent publication. Reauthorization and the final ready-state transition must serialize with the existing membership-change transaction, using a shared row-lock order or equivalent checked revision protocol. A stale worker cannot publish after a replacement attempt: use a claim/attempt token checked at publication. This policy is a recommendation requiring the product decision below, not an assertion that it was already accepted.
5. **Publication and download.** Write to an inaccessible temporary object, complete the file, and only then atomically publish its private object reference and ready state after the final policy check. Reconcile upload/database partial failure; clean orphaned objects. At every status/download request, check the actor's current ownership, tenant match, ready state and expiry against trusted server time. Use an authorization-gated streaming/proxy path where immediate revocation is required. A bearer storage URL issued before demotion can outlive authorization; merely shortening its lifetime does not establish immediate revocation. Do not publish permanent/public object URLs or rely on hiding the UI. Describe the in-flight request boundary explicitly: authorization at download start cannot retract bytes already delivered; stronger ongoing cancellation needs a defined requirement and supporting delivery path.
6. **Expiry.** Keep the accepted duration at seven days. Proposed timestamp: `expires_at = ready_at + seven days`, stored once using the service's UTC/time convention. Treat `now >= expires_at` as expired even if cleanup is delayed. Deny both file delivery and stale ready/status responses appropriately at this boundary; do not extend the timestamp on retries, polling or download. Any storage delivery mechanism must honor this deadline and revocation policy.
7. **Deletion and recovery.** Schedule idempotent deletion at expiry, with a periodic sweep to recover missed work. Keep deletion pending/retryable until storage confirms removal; distinguish access-expired from physically deleted. Handle already-missing files as success, bound retries, and surface persistent failures. Cover temporary objects, failed/revoked attempts, multipart uploads and orphaned files. Ensure storage versions, replicas, caches and backup handling meet the agreed retention meaning. Request-time denial provides expiry even during scheduler failure; it does not prove physical deletion. Seven days must not become “seven days plus an unspecified cleanup delay.”

An illustrative persisted lifecycle is pending → running → ready → expired → deleted, with failed/revoked terminal work states and separately tracked cleanup where needed. Match existing domain vocabulary. Store only necessary metadata: IDs, validated selection/schema version, state, attempt/claim identity, private object reference, ready/expiry/deletion timestamps and redacted failure category. Use database constraints and indexes for required tenant ownership, valid states and due-work lookups. Do not copy export contents into logs or job arguments. Scope object keys to opaque IDs; filenames and CSV cell escaping, if CSV is chosen, must be safe for consumers.

## Genuinely unresolved product choices

These are decision points for dependent implementation, not reasons to withhold the rest of this plan. Preserve any existing accepted policy discovered in the service before asking again.

- **Revocation and who owns a completed export.** Should demoting/removing the requester cancel their export even if another owner remains, or may the job continue for the organization and other current owners download it? Recommend cancellation and deletion on requester revocation, with every download still requiring current owner authority. Organization-owned continuation is feasible with strict current-owner downloads but changes the artifact's authority semantics. Also specify whether current owners may download another owner's export and whether a demoted-and-restored requester resumes or must request anew. Recommended revoked work stays revoked. These semantics are not settled by the fact that a job can outlive membership changes.
- **Retention anchor and deletion meaning.** Seven days is already accepted; do not reopen its length. Confirm whether seven days begins at successful file completion or request creation, and whether the promise is access expiry, physical removal, or both. Recommend completion-based access expiry plus deletion by the agreed deadline, with storage lifecycle and application cleanup covering failure. Request-based expiry gives a shorter download window after slow jobs. Physical erasure across backups/versioning must be feasible before promising it; an unavailable database/target cannot establish this fact. If existing policy already defines these details, reuse it.
- **Export contract, only where not already established.** Which record types/fields and attachments are in scope, what format clients need, and whether contents represent a consistent snapshot or a best-effort live scan. Recommend existing export conventions and a consistent snapshot when feasible. A PostgreSQL repeatable-read read transaction is a candidate, subject to actual version/driver behavior and long-transaction impact; batch-by-batch reads alone do not prove one snapshot. Do not silently export secrets or omit required records to simplify implementation. No new format chooser or filtering UI is necessary unless required.

Investigate queue behavior, supported storage deletion/versioning and authorization synchronization in code/configuration; these are technical facts to establish, not questions for the user to guess. Exact table names, helper names and test framework choices are routine implementation decisions.

## Delivery and recovery preparation

Use the existing deployment process and add the schema before enabling producers; verify worker compatibility before admitting exports. A feature flag or existing equivalent can gate admission. Promotion requires the authorization/race, persistence, expiry and cleanup checks above, plus confirmed deletion policy support. After an authorized deployment, verify the intended revision and owner/member journeys in the named target with non-sensitive test data, and check cleanup evidence. None of that is authorized or claimed as executed here.

If problems occur, disable new requests and publication/download as necessary while keeping access-expiry enforcement and cleanup active. Application rollback alone must not strand private files or restore expired/revoked access. Preserve additive metadata until jobs and cleanup have drained; reconcile stuck requests and artifacts, and avoid destructive schema rollback.
